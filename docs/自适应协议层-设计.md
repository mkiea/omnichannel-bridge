# 自适应协议层 · 设计

> 2026-11-19。起因：协议端太多（NapCat / Waylay / SnowCat / LLBot / PMHQ / Lagrange），
> **而且各自支持的 action 不一样、同一个能力叫法也不一样**。
>
> 本文回答两个问题：**要不要做**、**做到什么程度就该停**。

## 一、要不要做

**要。** 但理由不是"抽象更优雅"，是**已经发生的三次事故**：

| 时间 | 事件 | 桥受到的影响 |
|---|---|---|
| 10-30 | NapCat 退场，换 Waylay | `napcat-launch.js` 删掉，重写 `waylay-launch.js` |
| 11-10 | NapCat 删库 | 注入 DLL 失去上游 |
| 11-17 | QQ 升 9.9.37 | 注入点全废，协议端必须换 |

**每次换协议端，桥的"哪些能力可用"就重新洗一遍**。而现在这个信息**只存在于人的记忆里**。

## 二、做到什么程度就该停（边界）

**这是最重要的一节。** 不做边界，这个层会长成第二个框架。

### 只做四件事

| # | 做 | 不做 |
|---|---|---|
| **1** | **能力探测**（启动时问协议端"你会什么"） | ❌ 不猜、不按版本号硬编码 |
| **2** | **名字归一**（同义表：`send_group_forward_msg` ↔ `ForwardGroupSingleMsg`） | ❌ 不做参数结构的深度转换 |
| **3** | **降级**（缺就跳过，但**记一笔**） | ❌ 不伪造返回值 |
| **4** | **诊断**（一条命令列出"这个协议端缺什么"） | ❌ 不做自动切换/负载均衡 |

### 明确不做的三件事

1. **不追求"所有协议端行为一致"**——那是不可能的，也不必要
2. **不自动重试换后端**——一个 action 在 A 上失败就换 B，会让排查变成噩梦
3. **不做参数级适配**（比如把 `message_id` 的类型在 int/string 之间转）——**遇到就报错，让人看见**

## 三、四层结构

```
┌─────────────────────────────────────────┐
│  桥的业务层（播报/画像/积分/归档…）        │  只认语义，不认协议
└─────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────┐
│  ④ 诊断层                                │
│     adapter.probe() → 缺什么、叫什么      │
└─────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────┐
│  ③ 降级层                                │
│     不支持 → 返回结构化"不支持"            │
│     （不是 throw，是让调用方决定怎么办）    │
└─────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────┐
│  ② 归一化层                              │
│     同义表：语义名 ↔ 实际 action 名        │
└─────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────┐
│  ① 探测层                                │
│     启动时试调一组"探针 action"            │
└─────────────────────────────────────────┘
                    │
              协议端（LLBot / Waylay / …）
```

## 四、关键机制：探测怎么做

**不能靠"版本号 → 能力表"**（那会随协议端更新漂移）。**要实测**。

### 探针设计

```js
const PROBES = [
  { name: 'get_login_info',  cost: 'free' },   // 一定有的，用来确认连上了
  { name: 'get_group_list',  cost: 'free' },   // 群列表
  { name: 'get_msg',         cost: 'free' },   // 消息读取
  // 能力类：只读、无副作用、失败代价小
  { name: 'get_group_album_list', cost: 'free' },
  { name: 'get_essence_msg_list', cost: 'free' },
  // ⚠️ 绝不探针写操作（send_/set_/delete_）—— 会真的发出去/踢人
];
```

**三条铁律**：

1. **只探只读接口**（`get_*`），**绝不探写接口**——探测 `set_group_kick` 会真的踢人
2. **失败不等于不支持**——可能参数不对、可能权限不够。要**区分三种失败**：
   - `retcode = 1404`（action 不存在）→ **不支持**
   - `retcode = 100`（参数错）→ **支持，但用法不同**
   - 超时/网络错 → **未知，重试**
3. **探测结果要落盘**（`adapter-capabilities.json`），**下次启动直接读**，不用每次探

## 五、同义表长什么样

不用穷举所有协议端，**只登记"我们真的用到、且遇到名字分歧"的**。

```json
{
  "$comment": "语义名 → 各协议端的实际名字。没列 = 就用语义名本身",
  "send_group_forward_msg": {
    "llbot": "forward_group_single_msg",
    "napcat": "send_group_forward_msg"
  },
  "group_msg_emoji_like": {
    "llbot": "set_msg_emoji_like",
    "napcat": "group_msg_emoji_like"
  }
}
```

**维护原则**：**只在遇到时登记**，不预填。表里每一条都是"踩过的坑"，不是"猜的"。

## 六、成本评估（诚实版）

| 部分 | 工作量 | 说明 |
|---|---|---|
| 探测层 | **半天** | 探针列表 + 三种失败分类 + 结果落盘 |
| 归一化层 | **半天** | 同义表 + 查表逻辑（很薄） |
| 降级层 | **已有** | 现有代码就是"缺了就跳过"，只需补"记一笔" |
| 诊断命令 | **半天** | `node tools/probe-adapters.mjs` |
| **合计** | **约 2 天** | |

**后续维护成本**：每接一个新协议端，**加一行同义表 + 跑一次探测**（**10 分钟**）。

## 七、和现有代码的关系

**好消息**：地基已经有了。

| 已有 | 位置 | 说明 |
|---|---|---|
| **能力契约** | `docs/ADAPTER.md` | 8 必需 + 63 可选，**已经分了必需/可选** |
| **能力检测** | `lib/platform-adapter.js` 的 `inspectAdapter()` | **已经在检查缺什么** |
| **降级语义** | 同上 | "缺了只让对应功能降级" |

**缺的只有两块**：
1. **探测**（现在是静态检查，没有实测）
2. **同义表**（现在假设名字统一）

## 八、真正的价值

**不是"支持更多协议端"**，是：

> **把"这台机器上现在能做什么"变成一个可以随时回答的问题。**

今天的 10 轮实验里，最大的痛苦不是"跑不通"，是**"不知道跑没跑通"**——`hooks=4` 到底是成功还是失败，花了 4 轮才确认。

**自适应层的第一个产出不是"自动适配"，是"自动诊断"。**

# 补：两层协议要分开看（2026-11-19 修正）

> 主人指出：「实际上是两层协议，一个 OneBot 一个 Waylay，这俩是分开的」。
> 这句话推翻了我上面"一个自适应层"的说法——**必须拆成两层分别设计**。

## 一、两层各是什么

```
桥（业务层：播报/画像/积分/归档）
        │
        │  ← ① OneBot v11：JSON 消息、action 名、参数形状
        ▼
协议端（Waylay / NapCat / LLBot / PMHQ）
        │
        │  ← ② 客户端层：怎么起 QQ、怎么注入、怎么判活
        ▼
QQ 客户端（注入进去 / 自带内核）
```

| 层 | 负责 | 现有实现 | 差异性质 |
|---|---|---|---|
| **① OneBot** | 桥 ↔ 协议端的**通信契约** | `lib/onebot.js` | **名字/参数不同**（本质一致） |
| **② 客户端** | 协议端 ↔ QQ 的**启动与注入** | `lib/waylay-launch.js` | **流程完全不同**（本质不同） |

## 二、为什么必须分开

**因为它们的"可变性"不是一个量级**：

| | OneBot 层 | 客户端层 |
|---|---|---|
| 换协议端要改什么 | **加同义表一行** | **整个启动器重写** |
| 差异形态 | `send_group_forward_msg` ↔ `ForwardGroupSingleMsg` | NapCat 用 `NapCatWinBootMain.exe -q <uin>`；LLBot 用 `pmhq.exe` + 自有内核 |
| 能否通用探测 | **能**（只读 action 探一遍就知道） | **不能**（要真启动 QQ 才知道） |
| 失败代价 | 某个功能不可用 | **QQ 起不来** |

**所以合并设计会导致**：为了兼容一个"完全不同的启动方式"，把 OneBot 层也搞得很复杂——**而它们的抽象层次根本不一样**。

## 三、① OneBot 层：同义表 + 能力探测

按前文第五节做。**关键**：

```json
{
  "send_group_forward_msg": { "llbot": "forward_group_single_msg" },
  "group_msg_emoji_like":   { "llbot": "set_msg_emoji_like" }
}
```

**只登记实测遇到的**。今天已经实测出两条。

**探测**：只探 `get_*`，结果落盘。

## 四、② 客户端层：接口化，但不是"自动适配"

**这层不能做"自适应"**——因为启动流程差异太大，试图统一会得到一个谁都不像的抽象。

**能做的是"接口化 + 各自实现"**：

```js
// 每个协议端一个实现，接口只有 5 个方法
interface ClientLauncher {
  name: string
  detect(): Promise<{ installed: boolean, version?: string, exePath?: string }>
  start(opts): Promise<{ pid: number, port: number }>
  stop(): Promise<void>
  status(): Promise<{ running: boolean, injected: boolean, port: number, uin?: string }>
  logs(): AsyncIterable<string>   // 或返回日志路径
}
```

**现有 `waylay-launch.js` 就是这个接口的一个实现**（虽然没那么写）。

**新增 LLBot 时**，写 `llbot-launch.js`，实现同样 5 个方法——**不需要改动 Waylay 那个**。

**关键设计**：**"选哪个 Launcher"由配置决定，不由代码猜**。

```yaml
# 配置里写清用哪个
client:
  kind: waylay        # waylay | llbot | pmhq
  exePath: ...
```

**不做"自动检测有哪个就用哪个"**——那会让"为什么今天用的是 LLBot"变成一个谜。

## 五、两层的关系（重要）

**它们可以任意组合**，但有约束：

| 组合 | 可能吗 | 说明 |
|---|---|---|
| Waylay 客户端 + OneBot v11 | ✅ | 现状 |
| LLBot 客户端 + OneBot v11 | ✅ | LLBot 暴露的就是 v11 |
| **LagrangeV2 + OneBot v11** | ⚠️ | **V2 主推 Milky**，OneBot v1 已 sunset |
| 任意客户端 + 任意上层 | ❌ | **上层协议由协议端决定**，不是自由组合 |

**所以约束是**：**上层协议跟着协议端走**。换客户端 = 换协议端 = 换上层协议。

## 六、修正后的工程量

| 层 | 做什么 | 工作量 |
|---|---|---|
| ① OneBot | 探测 + 同义表 + 诊断 | **约 1.5 天** |
| ② 客户端 | 把 `waylay-launch.js` 抽成接口 + 写 `llbot-launch.js` | **约 2 天** |
| **合计** | | **约 3.5 天** |

**比合并设计多 1.5 天，但换来的是两层各自可独立演进**：
- 换协议端（LLBot）→ **只动 ②**
- 换上层协议（Milky）→ **只动 ①**

## 七、一句话

> **① 层做"归一"，② 层做"接口化"。**
> **前者可以自动探测，后者必须人工选。**
