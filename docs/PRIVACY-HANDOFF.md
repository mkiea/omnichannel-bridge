# 隐私泄露方向的作业说明

> 2026-11-18 立。**这是 `REDTEAM-HANDOFF.md` 的姊妹篇**：
> 那本让你打**功能**（能不能骗过检查），这本让你找**该藏起来却露在外面的东西**。
>
> 配套材料：`docs/PRIVACY.md`（判据与处置）、`docs/REDTEAM.md`（功能侧攻击）。

## 0. 一句话

**这个仓库是公开的。请找里面不该出现在公网的东西。**

不是找 bug，是找**泄露**。它不会让任何测试变红 —— 这正是要你来的原因。

## 1. 你手上有什么（这决定了你能做什么）

| 有 | 说明 |
|---|---|
| **完整的源码**（76 个模块 / 35k 行） | 注释、测试、配置 schema、文档全在里面 |
| **提交历史**（`git log`，上千条） | 旧版本可能还留着已经"脱敏"的东西 |
| **两份判据文档** | `PRIVACY.md` 定义了什么叫泄露，`REDTEAM.md` 讲了已知缺口 |

| 没有 | 说明 |
|---|---|
| 运行时 `profile`（含真实账号/密钥） | 已脱敏，不会给你 |
| `dataRoot`（会话、图片、事件流） | 真人的东西，**不要要** |
| 真 QQ 连接 | 不需要 —— 隐私泄露**静态就能查** |

**关键**：功能攻击在没真机时打不了，**隐私泄露恰恰相反** ——
它藏在文件里，而你**手上就是全部文件**。

## 2. 六种形态（按发现难度，越往后越少人查）

详细判据见 `PRIVACY.md` §1。这里给**每种怎么查**：

| # | 形态 | 怎么查 | 为什么难 |
|---|---|---|---|
| ① | **内容** | `git grep -nE '3[0-9]{9}'` 之类 | 容易，但**只能查到你知道该查什么** |
| ② | **文件名** | `git ls-files \| grep -E '[0-9]{5,}'` | 常被漏：内容干净、名字泄露 |
| ③ | **注释** | 读那些"实测：…""举例：…"的行 | **没人扫注释** |
| ④ | **白名单** | 找 `FAKE_IDS` / `ALLOW` / 豁免表 | **为了跑绿而加的例外，最容易夹带真值** |
| ⑤ | **提交历史** | `git log -S '<值>' --oneline` | 当前版本干净 ≠ 历史干净 |
| ⑥ | **契约不一致** | `grep` 人设/文档里的"系统会…"，再找实现 | 表现为"功能异常"，不表现为"泄露" |

**③④ 是重点**。这个项目的作者在一天之内两种各犯一次：
修隐私闸门时在注释里复述了真实号；在同一份文件的白名单里放了一个真实群号。**闸门自己成了泄露源。**

## 3. 判据：什么算泄露，什么不算

**算**（要报）：

| 类 | 判据 |
|---|---|
| **真实值** | 能指到具体的人/群/机器（QQ 号、群号、真实昵称、`C:\Users\<真名>`） |
| **凭据** | 任何形态的密钥——**包括看起来像假的**（可能只是"看起来"） |
| **研究资产** | 能反推出研究内容的（模型权重、训练脚本、数据集、人设规格、设计规范章节号） |
| **内部机制** | 泄露了"系统怎么实现的"（协议标记、状态机分支、provider 内部名称） |

**不算**（别报）：

- **明显的示例值**：`user` / `someone` / `example` / `2000000001` / `3000000001`
- **公开文献**：arXiv 编号、SWEBOK、Parnas 1972 —— 这些本来就公开
- **测试里的假密钥**（如 `sk-abcdefghij...`）—— 但**必须确认它是假的**才能放过
- **代码风格问题**（这不是目标）

**判断"是不是真的"的唯一方式**：看它**在不在运行配置里**。
运行时配置（`~/.dsh/profiles/*/cordis.patch.yml`）的 `allowUsers` / `allowGroups` / `botQq`
是真实值的锚点 —— 但那份**不给你**，所以你要靠"这个值看起来像真的吗 + 它出现在什么上下文"来判断。

| 项 | 状态 |
|---|---|
| git 历史里的旧真实号 | **未清**（当前版本已脱敏，旧 commit 还有） |

## 5. 交什么（格式严格）

每条一条记录，**四项齐全**：

```markdown
### [编号] 一句话

- **位置**：`path/to/file:行号`（必须能点到行）
- **原文**：那一行的内容，**但把敏感部分换成占位符**
     例：`const okState = run({ uin: '<12位号>' })`
- **为什么算泄露**：它指向什么（哪个人/哪个群/哪份研究/哪个内部机制）
- **严重度**：P1 凭据 / P2 真实账号 / P3 本机路径 / P4 研究资产 / P5 内部机制
```

**没给原文的不收** —— "某处可能有真实号"这种等于没找到。

**⚠️ 报告本身不能成为新的泄露源**：原文里只保留**上下文**（前后各几个字符），
敏感值一律占位符化。**你自己也不要把原文贴到任何地方。**

## 6. 三条禁令

1. **不外传**：找到的内容**不要**贴到任何第三方平台、不要喂给别的模型。
   报告只写占位符 + 位置。
2. **不改代码**：你出报告，不提交补丁。想验证就写临时脚本，不要进 `main`。
3. **不碰真实数据**：`dataRoot`、`profile`、任何 `qq-*.json|log|jsonl` —— 都不要读。

## 7. 开工前

```bash
# 1. 基线要先绿（红了说明环境问题，不是泄露）
node tools/verify.mjs --quick        # 期望 5 关全过（约 32 秒）

# 2. 跑一遍现有的两道闸，看它们报什么
node test/privacy-unit.mjs           # 41 条
node tools/repo-audit.mjs            # 五类硬编码判据

# 3. 它们**报不出来的**，才是你要找的
```

**这一步很重要**：现有闸门能查的东西已经查过了。
你要找的是"**闸门的判据本身有洞**"——比如它只查 10 位数字，那 9 位的群号就漏了；
它用 `\b` 做边界，那 `u_<号>` 这种写法就漏了。

## 8. 一句话给检查者

> **别从「哪个正则没写全」开始，从「哪份清单是我们自己维护的」开始。**

真实号名单、白名单、豁免表、示例值 —— 这些**为了"方便"而手工维护**的地方，
最容易同时藏着"漏检"和"新的泄露"。这个项目两个实例都出在同一类地方：
**为了让闸门跑绿而加的例外，最后变成了泄露本身。**
